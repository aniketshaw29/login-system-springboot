# 05 — JPA and Hibernate (ORM)

## What Is ORM?

ORM = **Object-Relational Mapping**. It bridges the gap between:
- **Java**: Object-oriented (classes, inheritance, methods)
- **SQL**: Relational (tables, rows, columns, JOIN)

Without ORM, you'd write:
```java
// Tedious JDBC code — pure SQL, manual mapping
PreparedStatement ps = conn.prepareStatement("INSERT INTO users (username, email, password) VALUES (?, ?, ?)");
ps.setString(1, user.getUsername());
ps.setString(2, user.getEmail());
ps.setString(3, user.getPassword());
ps.executeUpdate();
```

With JPA/Hibernate:
```java
// One line!
userRepository.save(user);
// Hibernate generates and runs the SQL automatically
```

---

## JPA vs Hibernate

- **JPA** (Java Persistence API): The STANDARD (interface/specification).
  It defines the annotations (`@Entity`, `@Id`, etc.) and API (`EntityManager`).
- **Hibernate**: The most popular IMPLEMENTATION of JPA.
  Spring Boot uses Hibernate under the hood by default.

Think of JPA as the "contract" and Hibernate as the "implementation".

## Entity Mapping

The `@Entity` annotation tells Hibernate: "This class is a table".

```java
@Entity
@Table(name = "users")     // → table name in DB
public class User {

    @Id                     // → PRIMARY KEY
    @GeneratedValue(strategy = GenerationType.IDENTITY)  // → AUTO_INCREMENT
    private Long id;

    @Column(unique = true, nullable = false, length = 50)
    private String username; // → column VARCHAR(50) UNIQUE NOT NULL

    @ElementCollection(fetch = FetchType.EAGER)
    @CollectionTable(name = "user_roles")
    private Set<Role> roles; // → separate table "user_roles" with FK
}
```

**Generated SQL (what Hibernate creates):**
```sql
CREATE TABLE users (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username   VARCHAR(50) NOT NULL UNIQUE,
    email      VARCHAR(100) NOT NULL UNIQUE,
    password   TEXT NOT NULL,
    active     BOOLEAN NOT NULL,
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);

CREATE TABLE user_roles (
    user_id BIGINT NOT NULL,
    role    VARCHAR(255),
    CONSTRAINT fk_user FOREIGN KEY (user_id) REFERENCES users(id)
);
```

## Spring Data JPA: Repository Magic

Spring Data JPA generates implementations automatically from method names:

```java
// You write just the interface declaration:
public interface UserRepository extends JpaRepository<User, Long> {
    Optional<User> findByUsername(String username);
    boolean existsByEmail(String email);
}

// Spring generates the SQL at startup:
// findByUsername → SELECT * FROM users WHERE username = ?
// existsByEmail  → SELECT COUNT(*) > 0 FROM users WHERE email = ?
```

**More examples of method name patterns:**
```java
findByUsernameAndEmail(String u, String e)
// → WHERE username = ? AND email = ?

findByUsernameOrEmail(String u, String e)
// → WHERE username = ? OR email = ?

findByCreatedAtAfter(LocalDateTime date)
// → WHERE created_at > ?

findByActiveTrue()
// → WHERE active = true

countByRoles(Role role)
// → SELECT COUNT(*) FROM users WHERE role = ?

findByUsernameContainingIgnoreCase(String part)
// → WHERE LOWER(username) LIKE LOWER('%part%')
```

## Transactions (`@Transactional`)

A **transaction** is a unit of work where either EVERYTHING succeeds or
NOTHING is saved (atomicity).

```java
@Transactional
public AuthResponse register(RegisterRequest request) {
    // If ANY of these steps throw an exception,
    // the entire transaction is ROLLED BACK.
    // No partial data is saved.

    checkUniqueUsername(request.getUsername()); // might throw
    String hash = passwordEncoder.encode(request.getPassword());
    User user = User.builder()...build();
    userRepository.save(user); // INSERT INTO users ...
    sendWelcomeEmail(user);    // if this fails, save is rolled back!
    return buildResponse(user);
}
```

`@Transactional` is handled by Spring via AOP (Aspect-Oriented Programming).
Spring wraps your method with:
```
BEGIN TRANSACTION
    try {
        yourMethod();
        COMMIT;
    } catch (Exception e) {
        ROLLBACK;
        throw e;
    }
```

## `ddl-auto` Values (application.properties)

| Value | What it does | Use when |
|---|---|---|
| `none` | Do nothing | Production (manual migrations) |
| `validate` | Verify schema matches entities, fail if not | Production safety check |
| `update` | Update schema if needed (safe) | Dev without data loss |
| `create` | Create schema on startup (wipes existing!) | Fresh dev start |
| `create-drop` | Create on start, drop on stop | Testing |

We use `create-drop` so each restart has a clean slate.

In production, use **Flyway** or **Liquibase** for managed schema migrations.
